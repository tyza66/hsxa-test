# hsxa-test：自然语言转 FOFA 检索

比赛方的目标与提交规范见 [docs/README.md](docs/README.md)，那是原始材料，只读。
这份 README 记的是我自己的解题思路：怎么理解题目、怎么选型、资料怎么收、
哪些事还没做完。

## 目标

输入一句自然语言资产搜索需求，输出一条合法、完整、可执行的 FOFA 查询语句。
100 道题，查询语句直接拿去 FOFA 上跑，按实际执行结果评分。

所以整个方案绕着一个前提展开：**判错方向的代价远高于答不出**。一条漏条件的查询
会搜回一堆无关资产，一条放宽了条件的查询又会漏掉该命中的。宁给固定答案，不硬凑。

## 思路是怎么演进的

### 一、起初按 Agent 做

第一反应把题目理解成"做一个 Agent"，于是先搭了命令行 Agent 工具
（[cmd/hsxa](cmd/hsxa/main.go)），架构选型是**链型**：一个请求沿着固定链路走完，
不搞多轮规划、不搞自主分支。设计目标是一问一答——喂进一句自然语言，结构化地返回
一条 FOFA 语法，附带置信度和判定依据，方便回归和评分。

### 二、读完 README 改做 Skill

通读 [docs/README.md](docs/README.md) 之后发现比赛方写得很清楚：不是让做一个 Agent，
而是"使用自己的 Agent、Skill、模型、规则或其他组合方案"，只按最终答案评分，
不比技术路线。既然 Skill 这条路投入产出更高，而时间有限，就决定**先做 Skill，
Agent 往后放**。

Skill 的形态也正好对症：把"哪个说法对应哪个字段、什么情况下必须放弃"这类判据
固化成文档，比每次现场推理更稳，也更容易做回归。

### 三、资料收集

- 抓了官方文档、GitHub `topics/fofa-api` 话题、FOFA 站点本身；有验证码的先绕开，
  先把能看的看完。
- 用 Playwright 走浏览器取页面内容，避免被反爬挡在门外。
- 资料汇总进 [rules/](rules/)。这里要特别说明权重：官方在会话里强调过，
  **`rules/3.txt` 的权重最高**，字段表以它为准；`1.txt` 是总纲，`2.txt` 是补充。
  Skill 里字段的运算符支持情况，就是从 `3.txt` 逐列解析出来、再与实现交叉对账的。
- `rules/` 是持续演进的规范源，**只读**，不往里写。

### 四、目录职责

| 目录 | 作用 |
| --- | --- |
| `docs/` | 比赛方原始材料：题目、答题模板、参赛包、README。**只读** |
| `rules/` | 随时更新的 FOFA 语法规范，字段表以 `3.txt` 为最高权重。**只读** |
| `test/` | 预留试验区，测试文件和结果都放这里 |
| `skill/` | Skill 本体：判据文档、脚本、答卷、回归套件 |
| `cmd/` `internal/` | Go Agent 脚手架（eino，链型），见下 |

### 五、后来把那套 Agent 也补上

时间上缓过来之后，决定把 Agent 侧也实现掉，方案是 **Go + 字节 eino 框架，链式**：
直接挂 Skill 的知识库做索引，查询语句的构建走 Skill 已经验证过的那条链路，
所以**不需要额外的压缩和变换**，Agent 只负责对话编排和把 Skill 的产出结构化。

eino 骨架已经跑通：`go build` / `go vet` / `go test` 全过，`AGENT_ENABLED=true`
下 CLI（serve/chat/tools）与 HTTP 冒烟、超限请求 400、优雅停机都验证过。
但**"索引 Skill 知识库"还没接上**，当前工具只有 current_time，知识库那一步
要等真实模型凭据联调。真正的主线成果始终是 Skill 和那份答卷。

## 更佳方案（没走的两条）

回头看，有两条比"人肉映射 100 题"更彻底的路：

1. **自动化网页回归**：用 Playwright 把生成的查询语句真的贴到 FOFA 上跑一遍，
   比对命中量与预期，让置信度从"待核"变成"已验证"。现在 `skill/tests/review.md`
   里那 27 条中低置信度，缺的主要就是这一步。
2. **直接拿到检索侧代码**：拿到网站本身或后端检索逻辑（等价于 API 的精确语义），
   字段匹配规则和运算符的真实含义就不用靠文档猜，直接对齐实现。

两条都受限于时间和访问条件，先记在这里。

## 耗时

约 2.5 小时。
