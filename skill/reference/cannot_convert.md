# 什么时候必须给固定答案

固定答案串（一字不差）：

```text
该需求不能直接转换为FOFA搜索语句
```

给错方向的代价远大于放弃：一条漏条件的查询会搜回一堆无关资产，一条宽容条件
的查询又会漏掉该中的。**表达不了就是表达不了，不要硬凑。**

## 一、取值本身不合法（最硬的一类）

| 情况 | 例 |
| --- | --- |
| 端口超出 1-65535 | 端口 70001、端口 1000000 |
| IPv4 段数不是四段或某段 > 255 | 1.2.3.4.5 |
| CIDR 掩码越界 | 10.0.0.0/999 |

这三类连同"同一字段既要求等于又要求不等于"由 `scripts/convert.py` 自动判定，
不需要模型再判。

## 二、条件之间自相矛盾

同一字段同时要求两种互斥状态。例如"国家代码必须等于 US，同时国家代码又必须
不等于 US"（M093）。注意别把**不同字段**的相反要求误判成矛盾——
`country="CN" && country!="HK"` 是两个字段语义下完全正常的收窄。

## 三、需要运行时信息或额外授权

FOFA 的索引里没有这些数据，查不到：

- 容器内部状态、进程内存占用等宿主机运行时指标。
- 需要登录或授权才能看到的内容。

## 四、纯主观且无可度量代理

"最安全的网站"、"最好的"——没有对应字段，也没有可量化的替代指标。若需求虽然
主观但存在公认代理（如"暴露在公网"→ 无私有网段条件），那仍算可转换，问题在
于有没有那个代理，而不在需求是否主观。

## 五、需要 FOFA 没有建模的维度

先查 `reference/fofa_fields.md`。字段表里没有的维度（例如具体的漏洞编号到产品
版本的映射、某类业务系统的枚举）不要用 `body`/`title` 模糊凑——那样的查询既
不准也不完整，宁给固定答案。

## 判断顺序

1. 取值合法吗？不合法 → 固定答案。
2. 条件互相矛盾吗？矛盾 → 固定答案。
3. 每个说法都能落到字段表里的某个字段吗？有落不了的 → 固定答案。
4. 第 3 步全部通过 → 组装查询，交 `lookup.lint()` 体检。

第 4 步产出的查询只要 `lint` 报错，**回去改写法，不要为了让 lint 闭嘴而删条件**。
